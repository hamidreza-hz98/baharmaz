# Deployment preparation and operations

No production host, domain, topology, backup provider or deployment configuration has been agreed. The existing `infra/compose.yaml` is an unauthenticated loopback-only development database, not a production configuration. Do not expose it publicly or deploy this project until the outstanding order, payment, SMS, delivery and release checks are resolved. When a host is selected, create and review a host-specific configuration with HTTPS termination, private application/database networking, trusted proxy, resource budgets and rollback before deployment. The project has not been deployed by this procedure.

## Build and configuration

Use the locked Node/npm versions in `README.md`, install with `npm ci`, and run lint, typecheck, format, unit, isolated integration and browser checks before `npm run build`. Keep build and runtime artifacts outside source control. `next start` serves the built app; a production reverse proxy must enforce TLS, request body and timeout limits, rate limiting, forwarded-header policy and upload concurrency. Provide all secrets through the selected host's server-side secret store and avoid values in command lines, repository files, logs, browser bundles or support tickets.

Do not configure real credentials or claim sandbox/live readiness without provider verification. SMS, payment, delivery zones and amounts require the separate business/provider decisions recorded in `otp.md`, `delivery.md`, `order-review.md` and `payment-outcomes.md`.

## Database, media and indexes

Estimate MongoDB disk for customer and order data, indexes, GridFS `media.files` and `media.chunks`, journal/oplog, temporary build/index space, backups and growth; set free-space and growth alerts. Media uploads can use 25 MiB input plus processing memory per request; enforce concurrency limits and budget for image decoding. Backups must capture both GridFS collections and metadata consistently with the rest of the database, be encrypted and stored off-host with tested retention and access controls. MongoDB replica sets, sharded clusters and managed services need topology-specific point-in-time backup and restore procedures; a live filesystem copy is not a substitute.

Before applying an index or data migration: record the intended deployment and database, take and verify a backup, inspect duplicates and capacity, run the applicable `npm run db:identity:indexes`, `db:cart:indexes`, `db:address:indexes`, `db:catalog:indexes`, `db:contact:indexes`, `db:delivery:indexes` and `db:order:indexes` commands with the approved environment, and verify the resulting indexes. These commands create indexes and do not use destructive synchronization. There is no general versioned migration runner; each future data migration requires an explicit tested migration and rollback/forward-repair plan. Never restore or drop against production by default.

The isolated `npm run test:backup-restore` test covers a cleanly stopped standalone copy, a synthetic document, GridFS bytes and two runs of the index scripts. It is not a production backup strategy and does not test an online snapshot, MongoDB Database Tools, a replica set, encryption, remote storage, deployment recovery time or provider backup service. MongoDB Database Tools were not available for an isolated `mongodump`/`mongorestore` exercise. Select a topology-specific supported backup, perform an isolated restore using that exact method, verify representative records and GridFS, record recovery time and permissions, and repeat regularly before launch.

On 2026-11-11, the isolated cold-copy restore and both index passes succeeded. A clean offline `npm ci` using the existing local npm cache, an isolated production build, and eight desktop/mobile production-browser smoke checks also succeeded. The registry was unreachable during an online install attempt, so a fresh network-based install was not verified; npm reported the peer-dependency warnings described in the README. No production deployment or provider was involved.

## Bootstrap, monitoring and rollback

After indexes and a backup, provision the single admin using `npm run admin:bootstrap` with `ADMIN_BOOTSTRAP_USERNAME` and a strong `ADMIN_BOOTSTRAP_PASSWORD` supplied securely for that one process; do not use a default password or put it in shell history. The bootstrap is repeat-safe and separate from the login UI. Remove temporary bootstrap secrets from the process environment afterward. See `identity.md`.

Poll `/api/health/live` for process liveness and `/api/health/ready` for MongoDB connectivity. Readiness does not verify indexes, storage capacity, provider connectivity or restore health. Monitor instance restarts, error rates, latency, rate-limit saturation, database/volume capacity, backup age and restore results. Configure log redaction and retention: do not record credentials, cookies, OTPs, message bodies, addresses, payment references or raw request bodies. The development fake can log OTPs and phone numbers and must not run in production.

For rollback, retain the prior immutable application build and its matching configuration; switch traffic back only after checking database/schema compatibility. Restore data only through a separately reviewed recovery plan into an isolated target, verify it, and authorize any production cutover explicitly. A code rollback cannot reverse persisted data or external provider activity. Define and test recovery objectives with the chosen host.
