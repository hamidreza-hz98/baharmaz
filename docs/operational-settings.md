# Operational settings and outstanding decisions

Administrators can manage the already-defined delivery-policy contract at `/admin/operational-settings`. The page accepts a complete JSON policy as documented in `delivery.md`; this is an operator-oriented interface for the existing validated contract, not an interactive map editor. It persists only after server validation and checks the document revision. Disabling delivery requires confirmation. Shop contact phones, social and chat links, address and map URL are managed at `/admin/content`; the established shop name and logo remain the existing application identity, with no newly invented identity fields.

No real delivery zone, fee, schedule, capacity, cutoff or closure has been approved. The presence of a policy editor does not constitute approval. Checkout quoting remains disabled until an authorized operator supplies the shop's actual rules; finite capacity remains unavailable until reservations exist. Order creation and transactional checkout remain unfinished. Other fee models, capacity and reservation behavior, and out-of-area exceptions require business decisions before implementation.

Provider choices and credentials are deployment configuration, not editable content. `OTP_SECRET`, `CONTACT_RATE_SECRET`, `AQAYE_PIN` and database credentials remain server-only; no provider setting or credential value is returned by the operational page. The production SMS provider is not selected or implemented, and live gateway payments remain blocked. Map tile and geocoding choices have their own availability, attribution and privacy constraints in the address documentation. See `.env.example`, `otp.md`, `payment-outcomes.md`, `addresses.md` and `delivery.md` for setup and limitations. Never paste credentials into the delivery policy or content fields.
