# Account changes and admin sessions

Customer personal information is available at `/account/personal`; `/admin/account` requires an independent admin session and is not linked from the public storefront. Both pages disable indexing and their APIs require the relevant server-side session. Admins sign in at `/admin/login`. Customer profiles store the optional Jalali birthdate as a validated civil date (`YYYY/MM/DD`), not a timestamp. Existing records need no data migration; unset birthdate, admin name and admin mobile are treated as empty. Admin username is normalized and validated, and optional mobile is normalized; changing it does not verify that phone as a customer number.

A phone change requires an authenticated customer with an already verified current number. The server issues a code for the current phone, then a separate code for the proposed new phone. The workflow is bound to the initiating session, has a ten-minute deadline, and codes are scoped to the specific change and step so they cannot be used for login or another change. The customer record is updated atomically only after both codes are consumed and all current phone, session, stage and expiration conditions still match. A duplicate number fails via the customer mobile unique index. `confirmNewPhone` checks that index exists before consuming the final code. Other sessions are not automatically revoked by a phone change; review this policy when account security and recovery rules are finalized.

The flow uses the OTP provider and limits from `otp.md`. **No production SMS provider is configured**; phone changes cannot be completed in production until the provider is implemented and verified. Fake delivery is explicitly development-only. The global limiter is a coarse shared ceiling and requires production edge controls. Interruptions or invalid/expired codes leave the old number unchanged; if delivery fails after a code was consumed, start a new change. Applying `npm run db:identity:indexes` remains required before enabling registration or phone changes.

Admin session management displays active admin sessions only. Revocation is restricted by admin ownership and session type. Revoking another session takes effect on its next protected request; revoking the current session also clears its cookie and returns the browser to admin login. Revocation does not affect customer sessions. Because no device fingerprint or IP address is stored, sessions display creation and expiry time rather than a device label.

Run `npm run test:integration` with the isolated MongoDB binary. The suite covers account ownership, Jalali date validation, partial/expired phone verification, duplicate mobile conflicts, cross-purpose OTP use, session isolation and current/other session revocation, including HTTP authorization and origin checks.
