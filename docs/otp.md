# Customer OTP authentication

Customer sign-in uses a four-digit SMS code only. New customers set a password after verifying their number, but password login is not offered. Existing customers, including admin-created mobile-unverified customers, receive a customer session only after successful verification. The dialog does not navigate away, so the current page and checkout state are preserved; the current guest-cart merge behavior is documented in `cart.md`.

## Configuration and operations

Set `APP_ORIGIN` to the exact public HTTPS origin in production and `OTP_SECRET` to an independent cryptographically random secret of at least 32 bytes. Store secrets outside source control. `OTP_EXPIRY_SECONDS` defaults to 120 (30–600), `OTP_COOLDOWN_SECONDS` to 60 (15–600), `OTP_MAX_ATTEMPTS` to 5 (1–10), and `OTP_MAX_SENDS_PER_HOUR` to 5 (1–20). Apply `npm run db:identity:indexes` before enabling authentication, including the customer mobile unique index and OTP/ticket TTL indexes. TTL cleanup is not used to decide validity. Unexpired challenge data contains phone numbers; restrict database access and backups accordingly.

There is no production SMS adapter or provider configured. Production sends fail closed until an approved provider, credentials and template are integrated and verified. No real SMS is sent by tests. To exercise locally only, set `SMS_PROVIDER=development` and `OTP_DEV_LOG_CODES=true`, `APP_ORIGIN` to the exact local origin, and a random `OTP_SECRET` in the untracked local environment. Development mode then prints the phone number and OTP in the server console. Never use real customers, share these logs, or enable this on an exposed environment; the fake is refused in production. Remove the flags when finished. The development fake is a diagnostic delivery mechanism, not a live SMS service.

## Security and limitations

OTP digests are HMAC-SHA256 keyed by the server secret, not plain or unsalted four-digit hashes. Challenges have per-phone hourly send limits, cooldowns and atomic verification attempt limits; successful verification atomically consumes the challenge. A shared database-backed global limit of 120 requests per minute provides a coarse additional ceiling without trusting forwarded client IP headers. It can be exhausted by a single attacker and needs deployment-specific edge/IP rate limiting and monitoring before production. Same-origin validation and JSON-only mutations protect this flow from cross-origin form requests; configure proxy host/origin handling correctly. The public send response does not depend on whether an account exists. Account state is revealed only after possession of a valid code. Avoid logging request bodies, phone numbers or codes outside the explicit local fake.

New-user verification issues a 10-minute HttpOnly one-use registration ticket. Invalid name or mismatched/short password can be corrected without consuming the ticket. An operational database failure after the ticket has been consumed requires the customer to start OTP again. Identity indexes must exist before registration; MongoDB should use least-privilege application credentials. Production authentication is not ready until a live provider is selected, its delivery behavior and abuse controls are verified, and the global throttle is reviewed for expected traffic. No password login is provided.

Run `npm run test:integration` with the isolated local MongoDB binary and `npm run test:e2e` after building. The integration suite tests fake delivery, failure, limits, expiry, one-time consumption, new and existing customers and the HTTP registration/cookie path. Browser tests use mocked responses; they do not send SMS.
