# Customer management

`/admin/customers` and its API require an independent admin session. The list filters by customer name or mobile (Persian and Arabic digits are normalized), supports verification filters and pagination, and shows global customer, unverified-mobile and paid-purchase summaries. Order count includes all order snapshots for the customer; purchase amount sums verified paid totals in integer rials, including shipping and discounts and excluding any unverified payments. The existing provisional order model has no refund ledger, so refunds and chargebacks are not deducted. A malformed verified payment makes the summary unavailable rather than silently counting zero. Orphaned orders whose customer no longer exists are excluded from the global amount. Review the aggregation's cost as the database grows.

The admin can create a name and unique normalized Iranian mobile; the account starts unverified and receives no SMS automatically. The existing OTP login verifies ownership and activates account access. Editing the name or entering the same normalized mobile preserves verification. Changing the mobile atomically clears pending phone changes, sets the new number unverified, and increments a customer session version. Existing customer sessions stop authorizing immediately and stay invalid after the new number is verified; the customer signs in again with OTP. This does not revoke an independent admin session. Conflicting mobile edits return a conflict rather than overwriting a newer number.

Back up the database and run `npm run db:identity:indexes` before enabling customer creation or editing; the service refuses writes without the unique mobile index. Existing verified customers and legacy sessions without a version use version zero, so there is no bulk migration. Existing unverified customers cannot use a customer session until OTP verification. The session version check is performed server-side for every protected customer request. Keep `APP_ORIGIN`, SMS provider configuration, and identity index setup as documented in the identity and OTP configuration. The existing order creation and refund limitations remain documented in `customer-profile.md` and `admin-dashboard.md`.
