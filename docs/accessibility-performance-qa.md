# Accessibility, responsive and performance QA

Review on 2026-11-11 used the HTML references in `design/screens` and the existing implementation. The dashboard and login references describe responsive desktop/mobile layouts; the implementation uses the RTL shell, mobile drawer, card/list views and Persian copy. This is not a complete pixel-by-pixel review of every screen. Checkout, payment, manual order creation and other unfinished workflows cannot yet be assessed end to end against final behavior.

Playwright now includes desktop (1280×720), tablet (768×1024) and Pixel 7 mobile (412×839) viewports. A focused run of the foundation shell, catalog, admin login and content editor passed 18 checks across all three viewports. These exercise RTL/mixed text, a measured button contrast ratio, keyboard focus and dialog dismissal, responsive navigation, image alternatives, horizontal overflow, catalog load-more failure/retry and delayed loading feedback. The admin profile menu now closes on Escape and returns focus; navigation icon buttons have 44×44 minimum touch targets. Hero and primary product images request eager/high-priority loading while catalog cards remain lazy. Stored images are resized and re-encoded to WebP; the current public endpoint serves a single processed size rather than responsive image variants.

A subsequent full foundation run was interrupted after 57 passing tests when the system drive fell below 50 MB free and the development server reported cache write failures. A later run in an isolated copy on a larger drive passed all 87 checks across desktop, tablet and mobile. Its fixture server logged a missing MongoDB configuration when a fixture link reached an actual protected admin page; the mocked checks still passed, but this is not evidence of that protected page's real authenticated journey. Automated checks cover representative controls, not every color contrast, image alternative, keyboard path, screen reader or screen. Run a full manual accessibility review and check the remaining reference screens before release.

`node scripts/performance-smoke.mjs` provides a local production-build diagnostic for the admin login page at the three viewports when `PLAYWRIGHT_CHROMIUM_EXECUTABLE` points to a local browser. It reports lab LCP, FCP and layout shift and checks overflow. It does not collect real-user field data, INP, a 75th percentile, a representative network/CPU profile, storefront metrics or a Lighthouse audit. It has not been run in this review because disk space prevented a fresh production build. Establish a safe consent-aware field measurement plan and run production-like mobile/network tests after freeing disk space; do not claim Core Web Vitals compliance from local synthetic observations.

Task 37 remains open until representative production performance measurements and the remaining manual design/accessibility checks are completed. No customer data or live provider calls are required for the focused browser tests.
