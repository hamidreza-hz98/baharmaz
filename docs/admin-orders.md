# Admin order management

The protected `/admin/orders` list searches snapshot order code, customer name or mobile, filters by status, and pages 20 at a time. Details show the historical customer, recipient, delivery, items, integer-rial totals and payment snapshot. Only admin status and an internal note (at most 1,000 characters) are editable. Notes and history are not exposed by the customer API. The status and note form shows a confirmation before saving; changing an order never initiates a payment, refund, shipment or notification.

The provisional lifecycle is `preparing → delivered` or `preparing → cancelled`. Delivered and cancelled are terminal, although internal notes may still be edited. These transitions are a conservative implementation of the existing provisional status vocabulary and require employer confirmation. Cancellation does not claim a refund. Payment is displayed as verified only if the snapshot contains both verified status and a valid verification timestamp.

An integer revision defaults to zero for existing records. Each write checks the revision and prior status, then atomically changes only the permitted fields, increments the revision and appends an audit entry to that same MongoDB document. The audit records the singleton admin ID, UTC time and old/new status and note; concurrent or stale writes receive a conflict. Audit history is bounded to 1,000 entries per order; when full, further edits fail and require an operator to investigate and design an archival procedure. It is not silently truncated. Database backups must include the whole order document and its audit array.

The Mongoose order model marks historical fields immutable, and the admin API rejects unrecognized fields. This protects this application's order-management write path; it is not a database-level protection against direct MongoDB writes or another model. Restrict database credentials and reconcile all writers when transactional order creation and payment processing are implemented. There is currently no real order-creation workflow, immutable snapshot creation transaction, payment ledger or refund integration. Task 29 remains open until those upstream contracts are implemented and the complete lifecycle and snapshot protection are verified against real application-created orders. Existing provisional records require no migration for the revision/note/history defaults. Back up the database before running `npm run db:order:indexes`.
