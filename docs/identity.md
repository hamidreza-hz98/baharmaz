# Identity and sessions

Customers and the singleton admin use separate collections. Customer mobile numbers must be normalized to `09` plus nine ASCII digits before storage. Admin bootstrap uses the fixed `_id` `primary`; concurrent attempts cannot create two singleton records and a repeat does not change the account. Passwords use Node's scrypt with random 16-byte salts, N=16384, r=8, p=1 and a 64-byte derived key. Passwords must be at least 12 characters and no more than 1024 UTF-8 bytes. Review work factors against production hardware and increase using a versioned rehash policy when needed.

## Setup

1. Configure `MONGODB_URI` and database access as described in `database.md`. Back up and review existing data and permissions first. Run `npm run db:identity:indexes` explicitly to create the customer mobile and session-token unique indexes and the session expiry TTL index. It does not drop indexes; duplicate data causes failure. Production startup deliberately does not create indexes automatically. Do this before accepting customer or session writes.
2. In a trusted terminal, set `ADMIN_BOOTSTRAP_USERNAME` (3–64 ASCII letters, digits, dots, underscores or hyphens) and `ADMIN_BOOTSTRAP_PASSWORD` only in the process environment, then run `npm run admin:bootstrap`. Use a unique strong password; no default exists. The command never prints the password or database error details. Remove the environment variables immediately afterward and do not put them in `.env.local`, shell history, source control or logs. Environment variables can be visible to privileged local processes; use an isolated administrative environment. Repeating or racing bootstrap leaves the existing admin untouched. Recovery or credential rotation requires a separately designed, authorized operational procedure.

## Session policy

`SESSION_DAYS` defaults to 30 and accepts 1–365. A year-long bearer session trades convenience for a longer exposure window if a cookie is stolen. Shorter expiration and explicit revocation reduce this risk. Tokens contain 256 random bits; only SHA-256 hashes are stored. Each request checks role, expiry, revocation and principal existence in MongoDB; TTL is cleanup only and is not relied on for authorization. Customer and admin use different HttpOnly, SameSite=Lax, path-wide cookies, marked Secure in production (HTTPS is required). Deleting a cookie alone does not revoke the server session: revoke it on logout, then clear the cookie. Fail closed if the database cannot be reached.

`createSession` is a server-only low-level primitive, not authentication: call it only after verifying the appropriate credential or OTP. `requirePrincipal` checks the correct cookie and database record; use it on every protected server read and mutation, and enforce ownership as well. Never accept a principal ID, role, or totals from the browser as proof of authority. SameSite cookies do not replace CSRF/origin checks for mutations. Rate limiting, OTP, login UI, session management UI, origin checks, account recovery and password changes are later tasks; no login routes are exposed by this foundation.

Run `npm run test:integration` with an installed local `mongod`. It creates an isolated temporary server and test database and exercises concurrent bootstrap, hashing, role isolation, expiry and revocation; no real customer data or external service is used.
