# Cart and pricing

Guest carts use an opaque 90-day HttpOnly, SameSite=Lax cookie and store only its SHA-256 identifier in MongoDB. Customer carts are keyed to the authenticated customer, and requests never accept a customer ID from the browser. On a cart request after sign-in, the server locks the guest cart, merges it into the customer cart, records the guest identifier atomically with the customer update, and clears the cookie. Retrying the same merge is idempotent even after a response is lost. A customer line and guest line for the same product are added together, with a temporary limit of 99 units per product; if the sum exceeds that limit the cart flags the capped quantity for review. The current provisional bounds are 50 distinct products and 1,000 merge/import identifiers per customer cart. If a bound or concurrent update prevents a merge, the guest cart remains locked to the same customer for a safe retry; do not delete it or change its owner without investigating the customer cart's merge ledger and backing up the database.

Older `lamsechi-cart-draft-v1` browser drafts are imported on the next cart interaction. A persistent random migration ID makes retries idempotent, including across guest-to-customer merge; the old local data is removed only after the server confirms import. Invalid or oversized legacy drafts are retained and cause an error rather than silently losing items. Cart updates use optimistic revisions internally. Product additions and quantity changes require a currently available product. Customers can remove unavailable or deleted lines. Existing lines record the price observed when first added; a later price change is explicitly flagged until acknowledged. Removed/unavailable lines remain visible but are excluded from the item subtotal and prevent checkout.

All item prices, regular-price subtotal and discounts are recomputed from current MongoDB product data using integer rials and overflow-checked arithmetic. The API returns `itemsTotalRials` after discount. **Shipping and the final payable total are null, and checkout is not ready**, because no delivery zone or fee rules have been approved. Task 21 must supply a server-authoritative shipping quote before a payable total or order can be calculated. Quantity limit is a safety bound, not proof of physical inventory. The `/cart` overview provides item editing and an address handoff. It rechecks cart state and prompts guests to sign in; the chosen address ID is stored only in the browser tab as a convenience, not as authorization or a delivery quote. Task 21 must revalidate address ownership, cart state and shipping rules on the server.

After backing up the intended database run `npm run db:cart:indexes`: it creates a TTL index for guest cart expiry. Customer carts have no TTL. Deleting expired guest carts depends on MongoDB's TTL monitor, and the cookie expiry is not a guarantee of immediate database deletion. Cookie and account sessions are bearer credentials; use HTTPS in production. A valid `APP_ORIGIN` is required for cart changes. Tests use synthetic data in isolated MongoDB; no production data or live services are used.

New anonymous cart allocations are limited globally to 240 per fixed minute across application instances; known carts and authenticated customers are unaffected. This also covers caller-supplied valid-looking guest tokens. Run `npm run db:identity:indexes` for the rate-bucket TTL index. The shared limit is a coarse ceiling, not a per-client defense: an abusive client can temporarily consume it, and an edge rate limiter remains necessary. A cart GET can create a guest cart and can merge a guest cart after sign-in; protect cross-site request exposure and infrastructure capacity accordingly until those operations are moved to origin-checked mutations.
